## Interfaces and data flow

1. GitHub `pull_request`, `push` to `develop`/`master`, nightly `schedule`, or `workflow_dispatch` starts the corresponding workflow jobs. The app workflow uses `contents: read`. In the Supabase workflow, database and integration jobs run on all four event types; the browser job runs its critical subset on PR/push and the full suite on schedule/manual dispatch.
2. Database/integration and browser jobs check out source and install locked pnpm dependencies plus Supabase CLI `2.119.0`.
3. Each Supabase job starts a project-local Docker stack and replays migrations/seed from scratch with `supabase db reset --local`. Database CI runs `supabase db lint --local --fail-on error` and `supabase test db --local`. Integration CI runs each existing race script in order; each script talks to the disposable database container and cleans its own synthetic fixtures.
4. The browser job obtains environment assignments from local `supabase status --env`, masks local publishable/anon/service-role keys, maps local `API_URL`/`PUBLISHABLE_KEY`/`SERVICE_ROLE_KEY` to the application and test environment, and fails if any required value is absent. Next.js and Playwright use only `127.0.0.1` services. CI runs one Chromium worker. PR and branch-push events run the selected critical specs; schedule and manual dispatch run all `tests/e2e` specs.
5. Unit CI runs Vitest with JUnit and V8 coverage enabled. A repository helper reads only the generated JUnit and JSON coverage summary, writes Markdown to `GITHUB_STEP_SUMMARY`, and Actions uploads JUnit/HTML/lcov/JSON artifacts after success or failure.

## Authorization and privacy impact

No product authorization behavior or Applicant/HR permissions change. Database functions and RLS are exercised locally only. The service-role key is generated by the per-job Supabase demo stack, marked as a masked value, supplied only to the fixture cleanup/test process and never saved in the repository or GitHub Secrets. Workflow permissions stay at `contents: read`; no privileged event or PR-comment token is introduced. All fixtures use synthetic data. Workflow output must not print the local key.

## Failure behavior

| Failure / adversarial input | Observable outcome / state guarantees | Verification |
| --- | --- | --- |
| Docker/local Supabase cannot start or migrations fail | Local DB job fails before lint, pgTAP or race checks; browser job fails before Playwright. No hosted target is configured. | CI-AC-02/03/04; start/reset output. |
| DB linter finds schema errors or pgTAP/race suite fails | Corresponding blocking job fails with its own check status. | CI-AC-02/03. |
| Supabase status omits URL/anon/service-role fields | Credential-export step exits nonzero; key-gated tests cannot pass by being skipped. | CI-AC-04; test the missing-field guard. |
| A PR adds a test whose local-only precondition is missing | Existing env-gated tests receive local credentials; status assertion prevents absent common credentials. Review should flag newly added unrelated skips. | CI-AC-04; review full and critical Playwright reports. |
| Unit test fails or coverage is zero/unavailable | Test command remains nonzero; summary/artifact upload runs with `always()` and gracefully records missing report files. | CI-AC-05. |
| Local test credentials accidentally appear in logs | Masking plus file redirection prevent expected disclosure; inspect workflow scripts for commands that print env contents. | CI-AC-07; workflow review. |

## Migration and backward compatibility

No database migration, runtime API or hosted Supabase configuration. Workflow CLI is pinned to the package lock version. Existing local commands remain available; new package scripts only orchestrate existing tests. Coverage is report-only with no new gate threshold.

## Rollout and rollback

CI configuration becomes active after merge to `develop`; the scheduled full browser run needs at least one hosted Actions execution to measure duration/stability. Require the resulting workflow checks in branch protection separately through GitHub settings; YAML cannot enforce branch protection. Roll back by reverting this issue's workflow, package, report helper and documentation changes. No hosted data or deployed application state needs recovery.
