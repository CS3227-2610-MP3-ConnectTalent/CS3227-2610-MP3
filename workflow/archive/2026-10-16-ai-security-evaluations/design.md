# Design: enforceable AI boundaries and measurable evaluations

## Runtime boundaries

Add a focused shared AI request guard before protected authorization/data work. Require JSON media type, deny a present Origin that differs from the request URL origin (including opaque `null`), and deny `Sec-Fetch-Site: cross-site`. Missing Origin is permitted for existing authenticated non-browser clients; it is not treated as authentication. Return no-store safe 403/415 responses, then retain the existing role/target validation and bounded streamed request reader. Test custom-domain/preview request origins; do not derive permissions from an untrusted Origin or weaken checks using arbitrary forwarded headers.

Separate provider configuration/transport/completion validation where responsibilities warrant it. Allow only `https://soclaas-api.comp.nus.edu.sg/v1` (equivalent trailing slash/default HTTPS port permitted), with no URL credentials/query/fragment. Permit HTTP loopback mocks only outside production. The endpoint is operator configuration, never user input. Do not follow provider redirects. A bounded fetch adapter must check actual streamed response bytes and cancel beyond 65,536 bytes before the SDK parses JSON; Content-Length alone is insufficient. Keep the SDK's 20-second deadline and zero retries, including while reading the body. Do not log rejected bodies or secret-bearing headers.

Accept one assistant completion with `finish_reason: stop`, no refusal/tool/function calls and nonempty content, then apply existing strict output schemas/source-ID mapping. A provider envelope/transport failure uses existing safe failure/final-audit paths. Missing/invalid results cannot become partial display content. Neither configuration nor transport changes expands model authority or data reads.

## Human control and prompts

Applicant generation produces a separate editable preview. Fixed application UI controls—not generated text—offer Use this draft / Replace current cover letter and Discard. State clearly that replacement changes only the local form; Save and Submit remain separate human actions. Do not overwrite current or newly typed cover-letter text when an asynchronous response arrives. Disable duplicate generation, handle target changes/stale results, retain notes on failure, and render preview text through ordinary text controls.

Refine prompts around task scope, source attribution and untrusted encoded/role-spoofing instructions without relying on prompt wording as the authorization layer. HR keeps sentence-ID-only model output, server-created bounded excerpts/questions, the original letter, and its separate human status action. Source selection can still be semantically wrong; do not call excerpt provenance a proof of correct assessment.

## Evaluation layers and reporting

1. Offline CI: use real prompt builders, schemas, source mapping and route/UI code with controlled provider boundaries. Cover at least 48 synthetic corpus cases across input surfaces and output attacks, plus benign controls. Assertions verify application properties; label results `contract`, not live model resistance. Include mutation-sentinel/spies proving no application/status/note/role writes or model tools, and sensitive-field canaries proving excluded data never enters payloads/reports.
2. Opt-in live model evaluation: compare captured baseline and refined prompts against the named `ai-security-v1-live12` dataset, six cases per feature, one trial per variant. Baseline means prompt text only; both variants use the same hardened transport and output contracts. Reuse production request/output contracts, not a permissive evaluator-only parser. Maximum 24 completion calls, sequential spacing of at least 10 seconds, no retries and a 20-second deadline. Verify the target/model before calls; stop on provider 429, invalid configuration or exhausted budget. Live access must be impossible in normal CI/offline mode, including when ambient keys exist.
3. Human review: evaluate Applicant unsupported claims and useful grounding, and HR evidence/gap correctness and neutrality. Structural/schema checks, exact source-ID correctness and attack-marker/fabrication flags are separate from semantic judgements. Use per-case rubric decisions; model text cannot mark itself passed or approve a release. One trial/case is a smoke comparison with limited statistical value.

Use an explicit offline command and a separately gated live command. Write a schema-validated metadata-only summary containing case/version/category/variant, observed check results, timing, safe error class and review-needed state. Never serialize raw errors or environment values. Store any raw synthetic material needed for human review only in ignored local `test-results/ai-evals/`, never product logs or CI uploads. Do not fetch real application records; no database credential is needed for the direct live model harness. No hosted app endpoint or application quota bypass is exposed by the runner; it is local operator tooling, and its separate throttling does not prove product quotas.

## Evidence, compatibility and rollback

Package scripts and CI run deterministic evaluations without live keys. Existing data/RLS/quota/withdrawal suites remain meaningful regression gates; run only the relevant local database/browser checks with synthetic fixtures, never reset existing/hosted databases. No schema migration is planned. Read installed Next.js route/form guidance before implementation. Apply test-first evidence to new guards, transport and preview behavior.

Document attack surfaces, limits, approval protection, actual results, failures and human-review gaps in the packet and a public AI-security/evaluation guide. Keep personal reflections student-owned. Roll back by reverting scoped app/prompt/evaluation changes or disabling AI using the existing operator flag; ordinary applications and HR review remain available. Do not weaken RLS/quotas, modify credentials or deploy as part of this task.
