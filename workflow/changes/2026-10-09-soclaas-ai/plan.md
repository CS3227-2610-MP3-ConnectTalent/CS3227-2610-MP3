## Goal, architecture, and stack

Deliver one limited SoCLaaS feature for each role. The Applicant route authenticates and authorizes before loading one published job, accepts bounded notes, calls the model once with only notes/title/requirements, validates a short draft, and returns it for manual editing. Generation has no persistence path. The HR route authorizes before loading one submitted application, sends only the frozen current letter and its job requirements, validates strict JSON, and returns display-only sections. HR status remains controlled by the existing explicit action.

Use two role-specific Next.js Route Handlers, focused server-only AI schema/provider/data modules, existing Supabase SSR session/RLS helpers, Zod, the installed OpenAI-compatible SDK pointed at SoCLaaS, and an additive PostgreSQL migration. Server-only configuration uses `SOCLAAS_AI_ENABLED`, `SOCLAAS_BASE_URL`, `SOCLAAS_API_KEY`, and `SOCLAAS_MODEL`; missing or disabled configuration fails closed. The migration freezes submitted letters in the database, preserves existing current values and original snapshots, and adds atomic per-user/deployment quotas plus metadata-only audit records. UI output remains ordinary React text. No provider tools, status writes, application writes, HR notes, or arbitrary lookup are added to either AI route.

## Global constraints and review focus

- Keep Applicant and HR routes and UI separate; check session and role before protected reads and before any model call. Use RLS and narrowly selected fields as additional controls.
- Treat notes, letters, requirements, model output, and provider errors as untrusted. Validate all inputs/outputs; use no provider tools; set one-call behavior, a 20-second timeout, and bounded input/output. Preserve the specified limits: notes at 4,000 characters, selected job requirements at 10,000, submitted letters at 5,000, draft output at 500 tokens/5,000 characters, and HR summary output at 350 tokens with three arrays of at most five strings of at most 240 characters each. Return stable safe errors without raw provider content.
- Enforce three calls per user and 60 per deployment per rolling minute with an atomic database reservation. Fail closed if the reservation/audit cannot be recorded. Do not automatically retry provider calls.
- Log actor, operation, target, timestamp and outcome only. Submission metadata is written with submission; existing `application_status_events` remains the HR status audit. Never persist or log notes, letters, prompts, output, credentials, or provider bodies.
- Verify malicious prompt text cannot reveal excluded fields or cause a status change. Keep the submitted letter visible beside HR output and clearly state that HR must verify the summary.
- Confirm the configured SoCLaaS model and key-specific limits before any live call. Use benign and adversarial synthetic examples; report those observations apart from deterministic security results.
- Before code, read the installed Next.js Route Handler and server/client boundary guidance (completed during packet preparation). Do not broaden this change into correction messaging, applicant ranking, job publishing, role promotion, or unrelated authorization refactors.
