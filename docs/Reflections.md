## AI security

The main trust boundary will be applicant-controlled notes and cover letters entering a model request. A letter could impersonate an instruction, ask for HR notes, or demand a status change. We therefore specified that HR notes never enter the prompt, the model has no tools, and status changes use a separate human-controlled endpoint. Authorization and data minimization need deterministic tests; prompt wording alone cannot prove security. We have not implemented or tested these controls yet.

The first job-browsing slice has no AI call. It still introduces a data boundary: public visitors should read published jobs but never drafts or closed jobs. The implementation uses both a filtered query and PostgreSQL row-level security. Seven local database checks passed for public visibility and write permissions, and three browser flows passed for filtering, details, invalid categories, and direct hidden-job URLs. This is evidence for the local stack; independent review and deployed verification are still pending.

The issue #6 Applicant implementation adds a useful pre-AI boundary: a saved cover letter is private even from HR until submission. The database grants no direct application write access to browser roles; three narrow functions check verified Applicant identity and the selected job's current state. A local pgTAP suite exercised other-user reads, HR draft denial, duplicate submission and edit denial after closure. The first submitted letter is stored separately from later edits so HR can compare versions. A separate reviewer found no confirmed database permission bypass. A local concurrency test observed three contested PostgreSQL lock waits before checking duplicate submission and closure outcomes. This remains local authorization evidence, not a prompt-injection or deployed security test; AI endpoints are pending.

Issue #8 adds another pre-AI boundary: only verified HR can create, edit, publish or close jobs, while Applicants and anonymous visitors can read only published jobs. The public RPCs call private-schema implementations that check the current HR role before touching rows. Published content stays fixed so a later AI summary and human reviewer use the requirements that applicants saw. Local database tests check direct-write denial and draft/closed visibility; browser tests exercise distinct Publish and Close controls. These results are local and do not establish hosted deployment.

Issue #9 exposed a subtler access risk: the earlier application SELECT policy allowed an owner to read a draft regardless of current role. A former Applicant promoted to HR could therefore still read that old draft. The new policy requires a current verified Applicant on the owner branch and limits HR to submitted rows. Local pgTAP checks the promoted-owner denial, Applicant/anonymous note denial, no direct note/event write grants, stale status rejection and review after job closure. A browser test exercises both roles with synthetic users and checks private-note denial. Status changes are a separate human form and database function, outside the future AI summary path. The audit currently covers successful and database-rejected note/status RPC attempts, not every invalid or unauthorized request; broader SEC-007 operational audit work remains.

## Spec-driven development

Issue #36 showed that distinct role pages alone did not make the account state clear: the public home still offered Sign in and My applications to HR, and detail pages omitted logout. The approved packet adds a single server-derived account navigation while keeping role authorization in page/action guards and RLS. Before implementation, focused tests failed ten navigation-state assertions and three logout-error assertions; the initial browser test found no consistent account navigation. These are concrete behavior failures rather than treating missing imports or a blocked test worker as the required test-first evidence. Logout provider failure needs its own visible retry outcome, rather than redirecting as if the session ended.

The first spec names both roles, one-application constraint, AI input/output boundaries, and release evidence. This made a course requirement conflict visible: the earlier scaffold assumed direct OpenAI use, while MP3 requires SoCLaaS. We changed the planned provider before implementing AI routes. A future spec revision must fix exact SoCLaaS quotas and model behavior before rate-limit code is written. Acceptance tests should challenge the intent, such as cross-user access and data leakage, rather than merely asserting the shape of a response.

The issue #7/#10 follow-up checked the configured SoCLaaS key instead of assuming the service-wide default: it allowed 30 requests per minute, so the approved application-wide cap is 24 to leave headroom, while per-user calls remain capped at three. Independent review also caught that an authenticated quota RPC could be invoked without making a model call. The fix confines quota/audit RPC execution to a server-only Supabase key and leaves applicant/HR content reads on the user's RLS session. A provider 429 now produces a safe retry-later response with a bounded retry delay when supplied; an observed live summary still misstated evidence, so structured output and injection resistance do not remove the need for HR verification.

For job browsing, the feature record translated ProductSpec v0.6 into observable cases: published jobs appear, category filtering works, details show the required fields, and direct draft/closed URLs reveal no unpublished content. The first browser run caught a missing semantic heading on job cards; fixing that markup made the browser suite pass. The record keeps independent review and human approval separate from passing automated checks.

For issue #6, the user decided that unfinished letters persist, submitted letters can be edited until job closure, the first submitted version stays available to HR, the limit is 5,000 characters, and signup requires email verification. Those choices were recorded in the proposal and deltas before coding. A focused validation test failed on a placeholder parser and passed after implementation. A separate browser test exposed an environment mismatch: the running Auth container still had confirmation disabled even though the config file was changed. Restarting the preserved local stack made the intended denial observable. The DB test did not have a captured red-first run, which remains a process evidence gap.

For issue #9, the student selected four status labels, add-only authored notes and manual HR promotion, then explicitly approved a packet defining transitions, data boundaries and the shared Development Supabase migration gate. The new pgTAP test failed on absent status/notes before the additive migration, then passed with the existing Applicant suite. A sign-in unit test failed because HR still went to `/applications`; role-aware routing made it pass. The first HR browser attempts exposed test timing and synthetic-data selector problems, which were fixed without changing access policy. The final focused HR browser run passed locally. This evidence does not imply that the shared preview database has been migrated or the feature accepted.

For issue #8, the approved JMG requirements already specified draft editing, explicit publication, fixed published content and closure. The new pgTAP test first failed 16 of 19 cases against the old database, then passed after the migration; later application-preservation cases brought the focused suite to 24. A focused validation test failed two assertions against a stub and passed after implementation. The browser test first found no HR jobs page; after implementation, a final denial check returned the sign-in page because the test navigated before Applicant sign-in finished. Waiting for the Applicant landing route fixed the test without changing authorization. The full local browser suite then passed 10 tests. This sequence distinguishes a product behavior failure from a test timing error.

After trying the site, the user requested a confirmation-password field and reported no Gmail message. The new browser test first failed because the field was absent, then passed after a server-side match check was added. The configured Supabase URL showed a local stack, so the expected message location was the local mail viewer. The UI and guide now state that directly. This example shows why user testing can reveal both missing input checks and confusing environment expectations even when the original automated flow passes.

On 5 October, we narrowed the product to one company's portal and one published opening. This removes employer onboarding and cross-company permissions from the first release. We also adopted `develop` for integration and `master` for releases. That branch flow records which code is ready for staging or production, while separate Supabase/Vercel projects are still needed to isolate runtime data and secrets.

Later on 5 October, the team proposed adding job categories such as Engineering, HR, Legal, and Sales. Spec version 0.3 expands the planned portal to several preconfigured openings for the same company. The application uniqueness rule now applies per applicant and job, and each AI request must use the selected job's requirements. Categories help applicants browse; they do not change permissions. This is a specification decision, not an implemented feature.

The later clarification was that the product should resemble a single employer's Workday careers page: all listings and applications belong to the company operating this deployment. Spec version 0.4 makes that identity boundary explicit and plans an HR publishing workflow. The design fixes a published job's requirements so the HR AI summary reviews the same criteria the applicant saw. This remains a planned behavior requiring implementation and tests.

The team then clarified that naming a fictional company is unnecessary. Spec version 0.5 treats the product as a reusable careers portal with neutral branding. Each deployment still serves one employer; supporting several employers in one deployment would need separate requirements and access controls.

The first GitHub Pages run failed because the repository had no Pages site. After enabling Pages, a second run failed because its deployment environment permitted `develop` while the publication workflow ran from `master`. Restricting that environment to `master` made the third run pass. This showed that a passing workflow definition alone does not establish a working deployment; repository settings and environment rules also need release checks.

## Basic multi-agent SE

The proposed analyst → implementer → independent reviewer handoff records the spec version, assumptions, changed files, and test evidence. A malicious instruction can enter through repository text, applicant data, or an agent's summary. The human owner must verify source material and review sensitive changes. This process is defined in `../workflow/AgentProcess.md`; actual agent runs, disagreements, and decisions still need to be recorded.

The issue #6 planning and implementation occurred in successive Codex turns. A separate read-only Codex reviewer later challenged SQL function privileges, RLS and retry handling against commit `f7ddb94`. It found no confirmed permission bypass but caught a misleading retry message and a concurrency evidence gap. The retry path now re-reads only the owner and selected job, and a server-action test checks the resulting notice. The first race test used `psql -c` and could not prove overlap; streaming commands with `psql -f -` plus `pg_stat_activity` lock-wait assertions made all three contested cases observable. The reviewer rechecked both corrections without editing or claiming to rerun the implementer's tests. The Applicant owner then accepted the local flow, and the accepted deltas were synced to v0.7 before archiving. This is a concrete benefit of a separate review: it improved both user-facing error handling and the quality of the evidence, while HR status and deployed checks stay open.

For #9, one Codex execution prepared the packet and implementation, so it could not count as an independent reviewer of its own SQL. A separate read-only Codex reviewer challenged RLS, grants, migration compatibility and test quality. It found that Applicant note/history privacy assertions ran before private rows existed. After HR writes, new direct Applicant/anonymous denial assertions passed; the reviewer rechecked the revised test without claiming an independent runtime run. It also identified incomplete audit coverage and pending shared-database compatibility smoke, both left visible in the record. Paul Cheng accepted the local feature with those limits on 2026-10-08; hosted rollout and release remain separate. The teammate's AI work has a narrow handoff: current submitted letter/revision and selected job requirements, with no note/status authority.
